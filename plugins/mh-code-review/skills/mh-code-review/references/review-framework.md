# 審查框架與檢查清單

## 錨定決策範圍與完成判準（掃描前必做）

Review 是拿「實際改動」比對「本次該達成什麼」。後者不固定下來，finding 只能拿通用工程常識當基準——同一份 diff 兩次 review 會得出不同的「這算不算問題」。掃描前先固定三行，🚫 不得跳過：

```text
審查對象：<精確的 diff 範圍／commit／工作樹狀態>
完成判準：<內容 ＋ 來源；未知則明示未知與採用的最低基準>
審查範圍：<納入、排除，以及允許補讀的相依範圍>
```

前兩項不可省：沒有審查對象，兩次看的事實就不同；沒有完成判準，就沒有一致的對錯判準。只剩審查範圍等於沒做錨定——它只回答看哪裡，不回答什麼算問題。

**哪些來源給得出完成判準**：使用者本次明確要求／指定的 Issue／AC、規格、契約或 API schema／PR description 與 commit message 宣告的本次目標。來源要連同內容一起寫下——同一句判準出自使用者明示、正式規格或模型推定，權威性完全不同。

⚠️ **只有宣告「應該是什麼」的東西才能當判準。** 描述「目前是什麼」的——現有實作、測試目前會過、log 與監控、既有寫法——只能當**證據**。既有行為要取得規範力，須有相容性承諾、具名下游依賴，或有權來源採納；🚫 不得把「本來就這樣寫」當成本次的完成判準。

**來源不一致時分兩種情況處理，🚫 不套單一條優先序**：

- **取代**：使用者本次要求與既有文件不同 ⇒ 以本次要求為現行承諾，既有文件退為「這次變更合不合法」的驗證依據。⚠️ **原始要求不自動優先**——已被有權者具名取代者，🚫 不得復活成現行承諾。
- **並列矛盾**：兩份都仍然有效、也都說得通，卻對同一件事給出不同答案 ⇒ 這件事本身就是缺口，列 Open question 交人裁決，🚫 不得挑一個繼續往下判。

**找不到完成判準時**：明示採用最低基準「本次要求 ＋ 既有具規範力的契約」，🚫 不得默默自行生成一套需求再據以判定，也 🚫 不得把既有行為升格成判準——它仍然只是證據。缺漏會改變 finding 判定時先補問；不會改變者依既有契約繼續，並在輸出中揭露這個限制。

⚠️ **錨不到判準 🚫 不抹除已觀測的後果**：安全邊界失守、資料不可逆損壞、錯值對外輸出這類後果照樣成立 finding，先止血；要據以**選定預期行為或改契約**，才必須等人裁決。

**找得到但欠定時**（判準容許兩種以上做法，而各自保住的性質不同）：回查當初的意圖，兩層各答一件事——**執行理念**給方向（原意是什麼、要保住什麼），**決策理由**給取捨（當初在哪些候選之間選、為什麼）。⚠️ 兩者只決定方向與候選，🚫 不直接成立 finding：要據以判定仍須落到具規範力的基準，落不到就是 Open question，不是 finding。

## 審查原則：Code-first, Finding-first

Review 的核心是**讀懂改動意圖，再判斷風險**，不是逐條比對規則。

1. 先依〈錨定決策範圍與完成判準〉固定審查對象、完成判準與審查範圍
2. 讀 diff，確認改動範圍是否與完成判準一致（有無混入不相關改動）
3. 從高風險往低風險掃描
4. 找到問題時，先依〈Finding 裁決〉的判定順序取得處置，再選呈現標記，並給具體修正建議
5. 沒問題就 LGTM，不要為了寫 review 而硬找問題
6. 風格意見不能偽裝成 blocking issue
7. 每個 finding 都要說清楚「為什麼是問題」
8. 不確定是否為問題時，用「確認：...？」提問而非直接斷言

## 審查優先序

按風險高低依序檢查，前面的比後面的重要：

| 優先級 | 面向 | 要問的問題 |
|--------|------|-----------|
| 1 | **行為回歸** | 這個改動會不會破壞現有功能？有沒有漏改的地方？ |
| 2 | **安全風險** | 有沒有注入、XSS、硬編碼密碼、敏感資訊暴露？ |
| 3 | **邏輯缺陷** | 邊界情況、null handling、off-by-one、例外處理？ |
| 4 | **架構一致性** | 符不符合現有 pattern？有沒有走捷徑繞過框架機制？ |
| 5 | **可維護性** | 下一個人看得懂嗎？命名清楚嗎？複雜度合理嗎？ |
| 6 | **效能** | 有沒有明顯的 N+1、重複計算、不必要的 I/O？ |

## Finding 裁決

正式裁決依 `mp-ai-guidelines` 問題裁決指南 §三（`claim_kind` 與 predicate）／§四（決策樹）——那裡是**唯一定義點**。本節放的是 review 用得到的子集與對應關係，**與指南牴觸時一律以指南為準**；🚫 不複製決策樹、🚫 不自建 predicate、🚫 不建裁決登錄表。

### 處置（terminal）

| 標題 | 處置 | 判定 |
|---|---|---|
| **本輪修正** | `FIX-NOW` | 屬本次範圍、修法局部明確，且 reviewer 或作者有權自行決定 |
| **阻斷回送** | `BLOCK/RETURN` | 問題成立，但本次無權裁決或需外部決策 ⇒ 回送 owner 或待拍板。🚫 不得改寫成 backlog，也 🚫 不得因為沒人承接就降成 `NO-ACTION` |
| **具名排程** | `SCHEDULE` | 延後處理，且 owner／批次／完成判準／接受者**四欄齊全**；少一欄即 `BLOCK/RETURN` |
| **裁決不處理** | `NO-ACTION` | 無合法到達路徑、無可觀測後果、純偏好，或修復不符目前規格／範圍。**不進 backlog** |
| **既決抑制** | `SUPPRESSED` | 命中既有 `NO-ACTION` 且無重開證據；**不輸出為 finding** |

⚠️ 這五個名稱與問題裁決指南一致，語意也一致。🚫 **不得沿用舊的 `BLOCK`／`FIX-IN-PR`／`FOLLOW-UP`**——`BLOCK` 在指南是「回送上游拍板」，與舊用法近乎反義，混用會讓同一個標記在兩份文件指向相反的行動。

### 判定順序（🚫 不得調整）

順序本身就是規則，不是流程圖排版。逐項問下來，問到哪個成立就照它走：

1. **強制義務**：使用者明確要求，或逐字引用的 `AC`、契約、法規、公司政策要求處理 ⇒ **不必先證明可達性與後果**，直接跳第 6 步
2. **受理門檻**：有合法觸發路徑 ∧ 有可觀測後果 ⇒ 繼續；缺任一項即指南的 `NOT-A-PROBLEM`——不建立 finding、不登記。**疑慮須作者確認才判得掉**時改以「確認：…？」提問，那是提問不是 finding，🚫 不佔配額、🚫 不得當成待辦
3. **本輪阻斷**：不修會使本次交付產出錯結果、契約說謊、必要操作失敗，或無法驗證完成判準 ⇒ 跳第 6 步
4. **受保護後果**：安全邊界失守／資料不可逆損壞／錯值對外輸出／既有契約被違反／主要流程不可用 ⇒ 跳第 6 步
5. **使用前攔截**：錯的東西在**被使用前**會被既有型別、驗證、測試、transaction 或 gate 擋下，且不擴散 ⇒ `NO-ACTION`；否則進第 6 步
6. **執行成本**：只決定由誰拍板，🚫 不決定要不要處理——
   - **從 1／3／4 進來**（非做不可）：局部、修法唯一、無契約與資料變更，且有權自行決定 ⇒ `FIX-NOW`；其餘一律 `BLOCK/RETURN`。🚫 不得逕自 `SCHEDULE`
   - **從 5 進來**：同上條件成立 ⇒ `FIX-NOW`；跨模組／跨 repo／需 migration 且四欄齊全 ⇒ `SCHEDULE`；四欄不齊而會擴散 ⇒ `BLOCK/RETURN`；四欄不齊又不擴散 ⇒ `NO-ACTION`

⚠️ **第 4 步在第 5 步之前，這個先後就是規則本身**：受保護後果 🚫 不因為「有 gate」「有監控」「有 alert」而降級。log／metric／alert 是事後偵測，🚫 不算攔截；尚未實作的測試、計畫補測、文件宣稱將擋下，同樣 🚫 不算。**證不出來就不算攔截**——沒有沿合法入口逐一檢查「錯誤產生點 → 第一個 consumer 使用點」之間的同步強制攔截，一律視為未攔截，🚫 不得因為「應該會被擋下」而落到 `NO-ACTION`。

⚠️ **成本永遠在最後，且 🚫 不提高前面任何一項**。難做不會讓問題變得更該做——否則大型重構天然就贏。成本只決定 escalation，不決定要不要處理。

### 一輪最多三項

**需新增工作的 finding（`FIX-NOW`／`BLOCK/RETURN`／`SCHEDULE`）一輪最多 3 項。** 超過先合併同根因再去重，🚫 不得硬列第 4 項；同一根因的多個症狀算一項，🚫 不拆成多筆。

命中強制義務、本輪阻斷或受保護後果者不受此限，但證據要齊。配額限制的是**輸出幾項工作**，不是准你省略裁決——超額候選一樣要走完判定順序，🚫 不得因為排在第 4 個就洗成 `NO-ACTION`。

### 沒有裁決 SSOT 的 repo 怎麼用（多數情況）

- `NO-ACTION` **可用**，但只是**本次 review 的當場判定**；🚫 不得在後續 review 假設此結論仍然有效。
- `SUPPRESSED` **禁用**——它必須命中 repo 內可讀的既有 `Won't fix`／`NO-ACTION` 裁決（issue tracker、裁決文件或既有 review 決定）。
- 🚫 **不得為了能用 `SUPPRESSED` 而主動建立新登錄表**，也 🚫 不替每個 finding 建永久 ID。

### 每個 finding 的最小證據

輸出為 finding 者一律附下列五項：

- **觸發路徑**：哪個合法輸入／資料狀態會到達
- **可觀測後果**：錯誤行為／錯誤資料／被違反的契約或不變量
- **處置**：上表五者之一
- **建議修法**：具體修正方向或程式碼
- **反向自證**：一行回答「**如果不處理反而是對的，最合理的情況會是什麼？**」。一個都想不出來，或寫出來全是支持修的理由 ⇒ 那是在幫既有結論辯護，不是在判斷，退回去重填證據欄

缺漏的效果**不相同**，🚫 不得一律降級：

| 缺什麼 | 處理 |
|---|---|
| 缺**觸發路徑**或**可觀測後果** | `NOT-A-PROBLEM`：不建立 finding、不登記；須作者確認者改以「確認：…？」提問 |
| 缺**處置**或**反向自證** | 視為輸出不完整、**不得交付 review**；🚫 不因此降低呈現標記（已證實的 SQL injection 不會因為忘了標處置就從 🔴 變 🟡） |

> 「可能影響」「未來也許」「最佳實務」不算證據。

## 🔴🟡🟢 是輸出格式，不是裁決語意

裁決結果只有上面五個 terminal。🔴🟡🟢 **只用於呈現**——PR review 要對應 GitHub 的 `APPROVE`／`REQUEST_CHANGES`／`COMMENT` 三值決定，自我 review 用它分區排版。**先判處置，再選標記**，🚫 不得反過來拿標記當裁決依據。

| 標記 | 對應處置 | 說明 |
|---|---|---|
| 🔴 | `FIX-NOW`（本輪必須修）／`BLOCK/RETURN` | 功能錯誤、安全漏洞、資料遺失風險、契約被違反 |
| 🟡 | `SCHEDULE`／不構成合併前置的 `FIX-NOW` | 效能問題、錯誤處理不足、已證實但可延後的邊界問題 |
| 🟢 | 無——**不是 finding** | 不影響正確性的可選觀察，不走裁決、🚫 不佔配額。PR review 可列 COMMENT，自我 review 通常省略。🚫 不得自動轉為 backlog |

- 🚫 **不得新增第四種標記**（如「⚪ 不修」）——`NO-ACTION` 是處置，不是標記。
- **同一處置內要排先後**時，排序鍵只能是判定順序的那幾項：本輪阻斷 > 受保護後果 > 使用前攔截不成立。🚫 不跨處置比較，🚫 不用數量或難度當排序鍵。

### 兩種模式的門檻差異

| 面向 | 自我 review | PR review |
|------|------------|-----------|
| 判定順序與處置 | 相同 | 相同 |
| 🟡 門檻 | 只報告**有合法觸發路徑與可觀測後果**的問題；純設計偏好、未證實的維護性疑慮、與本次完成判準無關的改善，不建立 finding | 保守，避免把偏好升格為阻擋 |
| 🟢 處理 | 通常省略 | 可列為 COMMENT |
| REQUEST_CHANGES | 不適用 | **僅限 `FIX-NOW`（本輪必須修）或 `BLOCK/RETURN`**；🟡 需重新走判定順序並落到這兩者才能阻擋 |

⚠️ **「數量多」不構成升格**：十個 🟡 仍是 non-blocking。要升格，必須說明它們**共同構成一個可觀測的高後果風險**（單一觸發路徑導致的多個症狀），而不是把計數當理由。

## Review 禁忌

- 為了寫 review 而硬找問題
- 把風格偏好包裝成 blocking issue
- 空泛批評不附修正建議
- 對人不對事
- 未讀 diff 就下結論
- 擴張到本次 PR 範圍外的無關模組或風格差異

## 檢查清單

依審查優先序排列。標有 **[PR]** 的項目僅適用於 PR review，自我 review 時可跳過。

### 🔴 高風險（必須確認）

**行為回歸**
- [ ] 改動是否影響現有功能的行為
- [ ] 相關聯的程式碼是否同步調整
- [ ] 是否有漏改的 caller / consumer
- [ ] 回傳值或資料結構變更是否影響下游

**安全風險**
- [ ] 輸入是否驗證與過濾
- [ ] 是否有 SQL injection / XSS / command injection 風險
- [ ] 是否有硬編碼密碼、API key、敏感資訊暴露
- [ ] 權限檢查是否正確（越權存取）
- [ ] 檔案上傳是否有類型/大小限制

**邏輯缺陷**
- [ ] 邊界情況是否處理（null、空陣列、零值、超長輸入）
- [ ] 錯誤處理是否完善（例外、失敗路徑、重試）
- [ ] 條件判斷是否正確（off-by-one、邏輯運算子）
- [ ] 型別轉換是否安全（隱式轉換、精度遺失）

### 🟡 中風險（建議確認）

**PR 範圍 [PR]**
- [ ] 改動範圍是否與 PR description / Jira 一致
- [ ] 是否混入不相關改動（格式化、重構混入 feature PR），建議作者拆分
- [ ] 分支是否已 rebase 到目標分支最新節點？落後時要求開發者先 rebase

**架構一致性**
- [ ] 是否符合現有 codebase 的 pattern 與慣例
- [ ] 是否有繞過框架機制的捷徑寫法
- [ ] 新增的依賴是否合理且必要
- [ ] 資料流是否符合分層架構

**可維護性**
- [ ] 命名是否清晰、意圖是否明確
- [ ] 複雜邏輯是否有拆分或註解
- [ ] 是否有重複代碼可抽取
- [ ] 函數長度與職責是否合理

**部署風險**（涉及 DB migration / API 契約 / 跨 repo / 環境變數時檢查）
- [ ] 是否有 DB migration？是否可安全 rollback？
- [ ] 前後端或跨 repo 是否需同步部署？有無時間差風險？ [PR]
- [ ] 此改動是否可安全 revert（無不可逆操作如 DROP COLUMN）？ [PR]
- [ ] 是否新增或修改環境變數（.env*）？對應的 .env.example 是否同步更新？

### 🟢 低風險（可選）

**效能**
- [ ] 是否有明顯的 N+1 查詢或重複計算
- [ ] 是否有不必要的 I/O 或大量資料載入
- [ ] 迴圈中是否有可提前中斷的條件
- [ ] 快取策略是否合理

## 常用 Review 術語

| 術語 | 意義 |
|------|------|
| LGTM | Looks Good To Me — 核准，沒問題 |
| NIT | Nitpick — 小問題，不阻擋合併 |
| PTAL | Please Take A Look — 請查看（通常用於請求 re-review） |
| WIP | Work In Progress — 尚未完成，先不 review |
| RFC | Request For Comments — 徵求意見，歡迎討論 |
