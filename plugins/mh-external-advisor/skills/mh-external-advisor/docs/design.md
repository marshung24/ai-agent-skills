# mh-external-advisor 設計文件

> 本文記錄設計理念、架構決策與驗證證據，供維護與擴充時參考。
> 使用面的輸出契約、參數、疑難排解見 `references/detail.md`；腳本內部行為、額度介面與底層指令見 `docs/internals.md`（各為單一事實來源，本文不重複）。

## 1. 目的與定位

讓呼叫端 AI（主要是 Claude Code）把其他 AI CLI 當「顧問」諮詢：非互動送出 prompt、取回純文字回覆，並能在**同一任務內延續同一段對話**（顧問記得前文）。

設計目標依序為：

1. **正確的 session 綁定**：延續的對話必須是「這個任務的那一段」，不能誤接到別段
2. **統一介面**：呼叫端對四個 CLI 使用同一套呼叫慣例與輸出契約，不需記各家差異
3. **誠實的失敗**：失敗要可診斷（exit code 分流 + stderr 保留），不靜默吞錯；診斷只抽錯誤訊息與事件型別，不倒回覆內容
4. **狀態最小化**：諮詢 adapter 不保存任何狀態（session id 由呼叫端持有）；唯一的耐久狀態是使用者的啟用清單，集中在清單層（§5.8）

## 2. 架構總覽

```
呼叫端 AI（持有 session id 於對話脈絡中）
   │
   │ ① 先取清單（唯一入口）
   ▼
┌─────────────────────────────────────────────┐
│ advisor-list.sh（getter）                    │
│  a. 掃 scripts/ask-*.sh          → 支援清單  │
│  b. 讀設定檔 enabled.json        → 啟用清單  │
│     （不存在／污損／空 → exit 4，印引導文）  │
│  c. 逐支取 ask-<ai>.sh --info，{SELF} 換絕對路徑 │
└─────────────────────────────────────────────┘
   ▲ 寫入                    │ 輸出「顧問 + 呼叫式」
   │                         │
┌──────────────────┐         │ ② 依輸出的指令呼叫
│ advisor-set.sh   │         ▼
│ （setter，驗支援）│  ask-<cli>.sh [-r <id>] [--] "<prompt>"
└──────────────────┘         │
                             ▼
┌─────────────────────────────────────────────┐
│ ask-*.sh（統一外殼）                          │
│  0. --info 自述（在 getopts/依賴檢查之前）    │
│  1. 依賴檢查（CLI / jq）        → exit 127   │
│  2. 參數解析（-r 延續目標）      → exit 2    │
│  3. prompt 取得（參數優先，stdin 次之）       │
│  4. [resume] 前置驗證（agy 專屬） → exit 3    │
│  5. 呼叫底層 CLI（stdout/stderr 分流暫存）    │
│  6. 解析回覆與 session id                    │
│  7. 輸出：回覆 + `[External Advisor <AI名> session_id: <id>]`        │
└─────────────────────────────────────────────┘
   │ 底層 adapter（各 CLI 差異封裝在此層）
   ▼
 codex exec │ claude -p │ opencode run │ agy -p
```

**分層原則**：
- **清單層與諮詢層分離**：呼叫端第一步一律走 getter，清單與呼叫式為執行期資料（§5.8）；adapter 只管單次諮詢，不知道也不在乎自己有沒有被啟用
- **adapter 骨架一致**：第 0–3、7 步四支 script 相同（統一外殼）；第 4 步（resume 前置驗證）僅 agy 有，第 5–6 步（呼叫方式與解析）依 CLI 而異，exit 3 語意與 id 缺失原因也有 agy 明示例外（見 detail.md exit code 表）。修改統一行為時四支需同步，但同步時勿抹平 adapter 特例
- **額度查詢不在諮詢路徑上**：`advisor-quota.sh` 不經 getter、也不透過 adapter 諮詢（只借其 `--info` 首行當標頭），直接走各 CLI 官方的額度介面；它是「還要不要再問一輪」的決策輔助，缺它不影響諮詢
- **新增 adapter 的唯一動作**：放一支支援 `--info` 的 `ask-<name>.sh` 進 `scripts/`——支援清單由檔案系統決定，getter／setter／文件皆無需登錄

**文件同步點**（internals.md 的「設計取捨」節是本文 §5 的使用面摘要，屬明文接受的重複；改版時依此清單同步）：

- resume 不自動重送政策：SKILL.md 使用方式、detail.md resume 失敗行為、本文 §5.2、四支腳本註解
- 免互動核可旗標與風險：README 安全前提、internals.md 設計取捨與底層指令、本文 §5.5、腳本註解
- 多段對話簿記規則：SKILL.md 延續 vs 開新、本文 §5.6
- exit code 契約：detail.md 表為 SSOT，SKILL.md 只留摘要、腳本 header 同步
- **清單腳本 rc=0／rc=4 的分支**：SKILL.md 使用方式、detail.md 清單腳本節（SSOT）、本文 §5.8
- **「有效 id 三判準」**：SKILL.md 取得延續用的 id（判準）、detail.md 擷取範例（寫法），兩者形狀不同、不得互抄
- **額度查詢**：SKILL.md 查額度小節（用法與結束碼摘要）、detail.md 額度查詢節（用法與結束碼 SSOT）、internals.md 額度介面節（各家介面與欄位 SSOT）、本文 §5.12（為何是這三個介面）
- **送出端規則**：SKILL.md 送出前兩條硬規則（副作用權限、預設背景）、detail.md 送出 prompt 的實務與背景執行節（需判斷、失效可逆的部分）、本文 §5.11。分界是「能寫成硬規則**且**每次諮詢都適用」——改版時勿把 detail.md 的判斷型內容升進 SKILL.md，那會稀釋守門條款

> 只有一份的東西不列在此：id 擷取範例僅存在 detail.md（README 只指路不放程式碼），各 adapter 的呼叫式僅存在該腳本的 `--info`。這是刻意的收斂——同一份 id 擷取範例曾並存 README 與 detail.md、且不在本清單上，結果兩處給出相反指導。
>
> **SKILL.md 刻意不連向 detail.md**（internals.md 同理，且更純為維護用）：典型諮詢路徑（送 prompt → 看回覆 → 依三判準取 id）用不到它，detail.md 只在「出事」（非 0 結束碼、接錯脈絡、掛住）或進階用法（背景、並行）時才需要——而 `advisor-list.sh` 的輸出末行已用**絕對路徑**指向它，時機與可用性都優於 SKILL.md 裡的靜態連結。留著連結的實際效果是每次諮詢都可能把 detail.md 讀進 context，去描述一個多數時候不發生的情況。

## 3. Session 延續協定

核心迴圈（呼叫端視角）：

```
首次：ask-x.sh "問題"          → 末行 [External Advisor <AI名> session_id: <id>]，把 <id> 記在對話脈絡
延續：ask-x.sh -r <id> "追問"  → 顧問帶前文回答；以本輪末行 id 更新簿記
```

- **id 由呼叫端保存在自身對話脈絡**（非檔案、非環境變數）。天然效果：呼叫端 `/clear` 後脈絡清空 → id 遺失 → 下次自動開新——「顧問 session 生命週期跟隨呼叫端 session」不需任何 hook。
- **每輪以最新末行 id 為準**：「resume 後 id 不變」是版本相依行為——部分 claude CLI 版本 resume 會 fork 出新 session_id，沿用首輪 id 會靜默遺失中間輪次。協定改為每輪更新簿記，對兩種行為皆免疫、成本為零。

## 4. 各 CLI adapter 差異

| 面向 | codex | claude | opencode | agy |
|---|---|---|---|---|
| 輸出格式 | NDJSON（`--json`） | 單一 JSON（`--output-format json`） | NDJSON（`--format json`） | 單一 JSON（`--output-format json`） |
| prompt 傳遞 | stdin（`-`） | stdin | 命令列引數（前置 `--`） | `-p` 的值（吃值旗標） |
| 免互動旗標 | `--dangerously-bypass-approvals-and-sandbox` | `--dangerously-skip-permissions` | `--help` 動態偵測（§5.5） | `--dangerously-skip-permissions` |
| id 來源 | `thread.started` 事件 | `.session_id` 欄位 | 事件頂層 `.sessionID` | `.conversation_id` 欄位 |
| resume 方式 | `exec resume <id>` | `--resume <id>` | `--session <id>` | `--conversation <id>` |
| resume 失敗偵測 | 非零結束碼 | 非零結束碼 | 非零結束碼 | **前置檢查＋回傳 id 比對**（見 §5.4） |

## 5. 關鍵決策（DECISION）

### 5.1 明確 id 定址，不用 `--last` / `--continue`
- **捨**：`codex exec resume --last`、`opencode -c`、`agy -c`（實作最簡）
- **取**：明確 id 定址
- **理由**：`--last` 語意是「當前 cwd 時間上最新的一段」，與任務無關。多任務交錯或換目錄會誤接到無關對話且**不自知**（實測：無前段時靜默開新、不報錯）。明確 id 天然綁定任務、不受 cwd 影響，且能與 CLI 回傳的 id 比對，驗證延續確實接上。

### 5.2 resume 失敗不自動 fallback 重送
- **捨**：resume 失敗自動改開新對話重送（體驗較順）
- **取**：exit 3 停止，由呼叫端決定是否重送
- **理由**：prompt 可能含副作用指示（跑指令、改檔案）。resume 可能在部分執行後才失敗，自動重送 = 重複執行風險。呼叫端是 AI，收到 exit 3 與說明文字即可自行判斷。

### 5.3 多行回覆解析必須在 jq 內取值
- **回歸案例**：`jq ... | tail -1` 意圖取「最後一則訊息」，實際取到「最後一行文字」——多行回覆被截斷，且 smoke test 用單行回覆（`OK`）驗不出來。
- **規則**：NDJSON 一律 slurp 整檔、在 jq 表達式內以 `last`/`first` 取「則」；禁止對 jq 輸出行用 `head`/`tail` 取「則」。

### 5.4 agy 的 resume 設兩道防線
agy 對無效 `--conversation <id>` 會**靜默開新對話且結束碼仍為 0**（stderr 僅有一行 `warning: ... not found`），其他三支靠非零結束碼判定 resume 失敗的方式在此不成立。故設兩道：

- **前置檢查**（送出前）：`~/.gemini/antigravity-cli/brain/<id>` 目錄不存在即 exit 3。攔在送出前，無效 id 零副作用——不送 prompt、不產生孤兒對話、不花一次呼叫。**只在能證明 id 不存在時才擋**：判準是 `brain/` 第一層**全部**為十六進位 UUID 目錄，出現任一非 UUID 目錄（分層或混合布局）即回報不可驗證——只要布局可能已改，「`brain/<id>` 不存在」就推不出「id 不存在」
- **回傳 id 比對**（送出後）：`.conversation_id` ≠ 傳入 id 即 exit 3，且**不輸出回覆**——該回覆來自一段無前文的新對話，輸出會被呼叫端當成延續結果採信

- **捨**：只留回傳 id 比對（零內部路徑耦合）
- **取**：兩道並存
- **理由**：前置檢查是唯一能做到「無效 id 零副作用」的位置。代價是耦合 agy 的儲存路徑，故無法確認結構時放行、僅靠事後比對——反過來擋下會在 agy 改動儲存結構後讓所有 resume 失效，而放行只是多花一次呼叫。**代價須誠實反映在契約**：exit 3 因此有兩種副作用保證，前置檢查擋下時 prompt 未送出，事後比對擋下時 prompt 已執行（見 detail.md exit code 表）

**id 取得**：`--output-format json` 的 `.conversation_id`。headless（`-p`）純文字模式不印 id，Auto-Save Resume 的「結束時印 resume 指令」僅互動模式；`--conversation` 只認 agy 自建的 id，自產 UUID 無效（靜默開新、不落地）。

**失敗判定採 fail closed**：CLI 結束碼非零、stdout 非合法 JSON、必要欄位型別不符、`status` 非 `SUCCESS`、`.response` 為空——任一項成立即 exit 1，不輸出殘缺回覆。最後一項與其他三支的「解析不到回覆即 exit 1」對齊，避免 agy 獨有「成功但沒有回覆」的 exit 0。

失敗時 agy 仍輸出完整 JSON（`status=ERROR`、`response` 為空、`error` 帶原因）而 **stderr 全空**，故診斷須從 stdout 取訊息，不能只印 stderr。

**診斷不倒 stdout 原文**（四支通則）：各 CLI 的輸出裡，一「行」就可能是整段回覆——agy 是單行 JSON、codex/opencode 的 NDJSON 一則事件即一行且 `agent_message`／`text` 事件內含回覆——以「行」設限等於不設限，會把回覆寫進呼叫端的錯誤日誌。改為只抽不含內容的欄位（agy 取 `.status`／`.error`，NDJSON 取錯誤事件訊息與事件型別序列），僅在無法解析時才 byte 設限倒原文。

- **捨**：`status` 未知值分流到 exit 2/3
- **取**：只有 `SUCCESS` 算成功，其餘一律 exit 1
- **理由**：agy 的失敗契約（逾時、斷網、認證失效時的 `status` 值與 stdout 完整性）未經實測，猜測映射會把未知狀態偽裝成已知語意

**回覆取出**：`jq -j` 直接輸出解碼後字串。不可用 `$(jq -r ...)`——command substitution 會移除尾端換行且無法還原。

### 5.5 保留免互動核可旗標（已接受的風險決策）
- **捨**：改為可設定項並預設安全模式（codex 有 `--sandbox read-only` 等選項）
- **取**：維持免互動核可旗標（codex/claude/agy hardcode `--dangerously-*`；opencode 因旗標名版本相依改以 `--help` 動態偵測，見本節末段），以文件明示風險與使用前提
- **理由**：諮詢型呼叫需免互動核可才能自動化，本 skill 的預設使用情境即為沙箱／受控環境；加設定項會增加介面複雜度，且「安全模式」在各 CLI 的旗標與語意不一致，統一外殼難以維持一致契約。
- **風險聲明**：這些旗標讓外部 CLI 跳過互動核可與沙箱限制——被諮詢的 AI 取得**與執行使用者相同的檔案、程序、網路與憑證權限，不限當前工作目錄**（可讀 `$HOME`、SSH/cloud 憑證、其他 repo，可對外連網），一句含副作用指示的 prompt、或被讀取內容中的 prompt injection，就足以觸發改檔案、跑指令、外送資料。**只有在已隔離檔案系統、敏感憑證、網路與宿主控制介面的 sandbox 中才可視為安全**——「容器」本身不等於安全（掛 Docker socket、注入 production 憑證、可自由連網的容器都不算）；已版控只防檔案損毀，防不了資料外洩與外部副作用。README 對使用者同步載明此前提。
- **旗標為版本相依（opencode 以 `--help` 動態偵測）**：實測證據鏈——1.17.10 的 `run --help` 列 `--dangerously-skip-permissions`；1.17.18 改列 `--auto`，但執行檔內仍含舊名字串、帶舊旗標呼叫仍成功（源碼 `run.ts`：`--auto` 公開、`--yolo` 與 `--dangerously-skip-permissions` 為 `hidden: true`，三者在 handler 內 OR 合併），即**約 1.17.12 起公開名更名為 `--auto`、舊名轉 hidden 相容別名**。故 `ask-opencode.sh` 不 hardcode、也不以版本號推斷，改以 `run --help` 偵測公開旗標名（公開名 `--auto` 優先、次選 hidden 舊名、皆無則 exit 127；`--help` 本身非零結束另報「能力查詢失敗」，不誤報成更名）：能力偵測不受版本字串、downstream build 影響，且在送出 prompt 前就失敗。**旗標名的比對一律用邊界比對**——子字串比對會誤中 `--autoupdate`，也會在 help 說明文字提及舊名時選到即將消失的別名。其餘三支 CLI 升版後仍需以 `--help` 重驗旗標存在。
  - 1.17.x 的觀測「opencode 對未知旗標不報錯（非嚴格解析）」**已於 1.18.18 失效**：實測未知旗標會 exit 1 並印 help，即旗標失效在 1.18+ 為顯性錯誤。此前提原本是動態偵測的主要理由（怕別名被移除後靜默失去核可）；前提改變後結論不變，理由改為向下相容仍只有舊名的 1.17.x。

### 5.6 穩定可靠優先的收斂決策
以「寧可少功能也要可靠」收斂三條使用規則：

- **使用者授權守門**：使用者買了哪些 AI 不一定，未經使用者指定可用的 CLI 不得主動呼叫（可詢問/建議）。裝機檢查（exit 127）只擋「沒安裝」，擋不了「沒訂閱/不想用」，授權是更上位的閘（自主模式把這道閘從逐次前移到一次性宣告，未推翻本條，見 §5.13）
- **多段並存靠呼叫端簿記，不可靠時退化為每 CLI 一段**：script 只能偵測無效 id（exit 3），「有效但屬別段」的 id 無法偵測、會靜默接錯脈絡。故允許多段並存，但呼叫端必須維護「CLI／主題／id」對照（SKILL.md 為此協定的 SSOT）；歸屬無法唯一對應時不延續、一律開新並附齊背景——簿記失守時自然退化為每 CLI 至多一段，錯配面收到最小。配套原則「延續是優化非必需，不確定一律開新」
- **子 Agent 只能接單次自包含委派**：跨 agent 邊界傳遞 id 會產生 owner 沒看過的前文，之後任一方延續都是盲區。故可委派的形態只有一種——主 Agent 附上呼叫式、子 Agent 不帶 `-r`、不回報 id。不另設「禁用子 Agent 諮詢」的閘：三層清單下子 Agent 天然沒有授權層（授權來自使用者在主 Agent 對話中的點名），該閘已冗餘；真正載重且 L3 擋不到的是**轉述不構成授權**——委派內容裡出現 CLI 名稱會讓子 Agent 誤以為授權成立，須明寫
- 配套修正：開新路徑補 CLI 結束碼檢查（非零即 exit 1，不信任殘缺輸出）、agy 的 id 套 `^[A-Za-z0-9-]+$` 字元集驗證（比其他三支嚴，因該 id 會拼進 `brain/<id>` 路徑，須防路徑蒙混）

### 5.7 其他工程慣例
- prompt 盡量走 stdin（codex `-`、claude），免長字串/特殊字元引號轉義；opencode/agy 受 CLI 限制走引數
- stderr 一律留檔，失敗時隨診斷印出（`2>/dev/null` 吞錯會讓失敗死得不明不白）
- 不用 `set -e`：失敗路徑需分流處理（exit 1/2/3/127），不可讓非零結束碼直接中止
- 變數後緊接全形字必須 `${VAR}` 加大括號——bash 會把多位元組字元首位元組黏進變數名（`set -u` 下報 unbound variable）
- 跨平台（macOS + Ubuntu 容器）：避免 `stat`（旗標不相容），以 `ls -td` 排序 mtime

### 5.8 顧問清單三層化
- **捨**：把「使用者擁有哪幾支」寫死在 SKILL.md（`AVAILABLE-CLIS` 標記區塊 + frontmatter description 的「（擁有：…）」，兩處須人工同步）
- **取**：三層分離——**支援**由 `scripts/ask-*.sh` 的存在決定、**啟用**由 setter 寫入使用者設定檔、**授權**由本次對話的點名決定；SKILL.md 只留流程指令，清單與呼叫式一律執行期取得
- **理由**：
  1. 寫死的清單是**別人的配置**。skill 隨 repo 公開發佈，第三方 clone 得到的是作者擁有的四支，而非自己擁有的
  2. 「擁有」與「支援」混在同一份清單，才需要「異動時兩處一併更新」的同步規則；分層後 description 談支援（固定事實）、設定檔談啟用（因人而異），同步點自然消失
  3. 裝機檢查（exit 127）只擋「沒安裝」，擋不了「沒訂閱／不想用」——啟用清單補的正是這段
- **為何是 setter/getter 而非讓 AI 直接讀設定檔**：清單的解讀規則（污損退化、adapter 遺失、`{SELF}` 路徑展開）集中在一支腳本裡，呼叫端只認 rc；設定檔格式日後要改也不影響呼叫協定
- **設定檔位置**：`${XDG_CONFIG_HOME:-$HOME/.config}/mh-external-advisor/enabled.json`。查證過：XDG 是 Unix 通用規範而非 AI Agent 規範（四支 CLI 自己 3:1 不一致——Claude/Codex/Gemini 用 `$HOME` dotdir，只有 opencode 走 XDG），本 repo 亦無既有約定。選 XDG 的實質理由是：設定檔的擁有者是這支 skill（一支 shell 工具）而非任何 agent，且放 `$HOME` 之下重裝 skill 不會被覆蓋、不可能誤進公開 repo
- **SKILL.md 只放流程、不放清單**：流程指令（getter 怎麼用、rc 怎麼分支）不會過期，清單會。理由本身寫在此處而非 SKILL.md——維護者改版時看得到，呼叫端載入 skill 時不必讀


### 5.9 `allowed-tools` 刻意不含 Bash
- **捨**：把 `Bash`（或本 skill 的腳本路徑樣式）列入 `allowed-tools`，讓呼叫免權限詢問
- **取**：只列 `Read` 與 `AskUserQuestion`
- **理由**：
  1. `allowed-tools` 是**預核准清單、不是安全邊界**——清單外的工具仍可用、照常詢問。所以列進去的唯一效果是「不再問使用者」，沒有宣告用途的作用（那是 `description` 的事）
  2. 本 skill 的 Bash 會拉起帶 `--dangerously-*` 的外部 AI CLI（§5.5 的風險）。免詢問等於拿掉送出前的最後一次人工確認，與本 skill「逐次授權」的守門設計直接衝突——權限詢問在這裡是功能，不是摩擦
  3. 以腳本檔名寫樣式無效：權限比對的是**指令字串前綴**，而協定要求呼叫端使用 getter 給的絕對路徑，開頭對不上。寫了會變成「看起來有設定、實際是空的」，比不設更誤導；改寫絕對路徑則綁定單一安裝位置，對公開發佈的第三方無意義
  4. skill 隨 repo 公開發佈，放寬的預核准會被第三方直接繼承，而其環境未必是 sandbox
- **註**：此欄僅 Claude Code CLI 生效，Codex／Gemini CLI 會忽略——不可當成跨 agent 的一致保護

### 5.10 採信原則用「硬規則」而非「重要度判斷」
- **捨一**：逐則分類再處置（事實／判斷／否定性主張三分類）——判準正確但成本壓在**每一則**回覆上，而絕大多數回覆是對的，等於對正確內容課稅
- **捨二**：「預設相信 + 重要度高／影響性廣／與認知衝突才查證」——三個 trigger 全是自我評估，而查證是額外工作、呼叫端有完成任務的傾向，「這則應該還好」是很自然的自我說服，實務上會往「全部相信」滑
- **取**：**兩條零歧義硬規則**（顧問給可執行證據就跑、要據以刪改既有內容就查）+ 三個訊號降級為「提高警覺」；不明寫預設立場——「預設相信」與「可執行證據就跑」並列會推著呼叫端執行顧問給的指令，而顧問回覆是不可信輸入（可能受 prompt injection 影響）
- **理由**：不需判斷的規則才擋得住趕時間的自己。兩條硬規則都滿足「成本近零、判準無歧義」：
  1. **可執行證據必跑**——顧問的判斷可能偏，但至少是它真的這樣想；它宣稱的實測結果可能根本沒跑，而這是最好查的。實例：顧問曾宣稱「實測 rc=0 且腳本被執行」，照其步驟跑實為 rc=4、未執行
  2. **刪改既有內容必查**——判準從「這則主張重不重要」延伸到「我要拿它做什麼」。既有內容是有人做過決定才存在的；否定性主張三個訊號通常都不觸發，但照做的結果是不可逆的刪除
- **另記**：「照建議改完必須自測」不屬採信原則而屬工程紀律——建議本身可能沒錯，套進具體情境才長出問題（實例：改為整份 schema 驗證後，`--add` 會把使用者原本設好的顧問一起清掉，任何採信規則都攔不到，只有測試會）

### 5.11 不做通用 prompt 模板，改以「送出端兩條硬規則」
- **捨一**：由 wrapper 自動前置一段通用顧問 prompt。讓顧問動手改檔本來就是合法用途，硬編唯讀會擋掉；加開關則違反 §5.5 的「不加設定項、維持介面單純」。更根本的是**不應把文字約束包裝成安全機制**——那是送給高權限模型的措辭，不是 sandbox；真要可靠只能在 OS／容器／credential 層限權，不存在「完整權限 + 零介面成本 + 可靠阻止越權」的 prompt 技巧
- **捨二**：把諮詢技巧整套寫進 SKILL.md。SKILL.md 每次觸發都載入，收進軟建議會訓練讀者略讀，稀釋真正的守門條款
- **取**：SKILL.md 只加兩條，與「採信原則」的兩條硬規則構成送、收兩端對稱——① prompt 須明示副作用範圍，未明示不得呼叫；② 預設背景執行
- **入選判準**：**能寫成硬規則**（可檢查、不需判斷）**且每次諮詢都適用**。據此降級進 detail.md 的有：「要求顧問標示證據等級」（執行者是顧問不是呼叫端、且只有 review 類用得到）、「清單是最低覆蓋集合／找盲點時不給清單」（需判斷，且失效可逆——重問即可）
- **副作用權限為何是硬規則**：這是四項提案中唯一失效不可逆的——顧問改壞未提交的工作區、或把讀到的憑證隨回覆外送，事後採信原則攔不到。且措辭刻意用「副作用範圍」而非「不得增刪改檔案」：後者漏掉 git 寫入、網路請求、啟停服務、改資料庫、發訊息、起容器，而「檢查」本身（測試、build、formatter、套件管理、docker）也不必然唯讀
- **暴露的設計真空**（尚未處理）：三層清單（支援／啟用／授權）管的是**能不能呼叫**，完全沒管**顧問能對環境做什麼**。使用者同意「問顧問」不等於授權顧問修改環境；本節的送出端規則只是以文件補位，不是真正的權限層
- **背景執行為何是硬規則**：原判準「有沒有可平行推進的工作」只衡量計算利用率，漏掉互動延遲。呼叫端即使無事可做，背景化仍讓使用者立刻取回控制權——「使用者沒被擋住發言、只是收不到回應」技術上成立，產品效果仍是對話被單向阻塞數分鐘
- **句尾不放「背景規則見 detail.md」**：與 §2 明載的「SKILL.md 刻意不連向 detail.md」衝突——連結會讓 detail.md 每次諮詢都可能被讀進 context，而 getter 輸出末行已用絕對路徑指路。只留決策規則、不放指路

### 5.12 額度查詢走官方介面，不讀私有 log、不引進第三方工具
- **捨一**：讀 codex 的 rollout log（`~/.codex/sessions/**` 的 `token_count` 事件確實帶 `rate_limits`）。路徑、檔名與 schema 皆為非公開實作細節，且同一份 rollout 有多筆 `token_count`，還要另定何者為準
- **捨二**：引進 CodexBar／ccusage。ccusage 讀本機 log 做歷史用量與成本估算，答不出供應商回傳的餘量與重置狀態；CodexBar 查 codex 額度走的正是本節採用的 `account/rateLimits/read`，引進它只多一層第三方 binary 的供應鏈、版本相容與容器持久化維護
- **取**：三家官方的非互動介面——codex 走 app-server 的 JSON-RPC `account/rateLimits/read`，claude 與 agy 走 CLI 內建的 `/usage`。皆不啟動對話輪次
- **為何不順道報單次 token 用量**：訂閱制下稀缺的是額度窗而非 token 數，且 token 數無法反推扣掉多少額度（額度按 token 成本比例扣）。單次 usage 三家 stdout 都現成，要用時再加，與本節無關
- **必須驗證命令真的走內建路徑**：claude 認 `.num_turns == 0`、agy 認 `.command.name == "usage"`。若某版本改把 `/usage` 當一般 prompt 送進模型，回覆會是模型編出來的說法——不驗就等於把幻覺當額度，還白費一次額度
- **codex 的 app-server 必須保持 stdin 開啟到收到回應**：stdin 一旦 EOF，它會在回應前就結束（實測無輸出），故以 fifo 持有寫端；但它也會**繼承**該寫端，只關父端等不到 EOF，會孤兒化存活到 timeout（實測），故啟動時即以 `{W}>&-` 關掉其繼承的寫端
- **收工不主動 kill，而是關寫端後續讀至 EOF 再 `wait`**：這是為了讓結束碼可解讀——提前停讀會讓 server 寫後續通知時吃 EPIPE，主動 kill 則讓結束碼只反映自己下的訊號，兩者都會使下一條的第一道防線形同虛設。代價是 server 若不理會 EOF 會停滯至 timeout 並拒收該次回應（見已知限制）
- **fail closed 的兩道防線**：CLI 結束碼非零一律不採信輸出，三支皆適用（半截 JSON 仍可能通過欄位檢查）；百分比先驗型別與範圍再換算（越界值會印出負數或大於 100 的假餘量，給錯數字比查不到更危險）
- **`timeout` 列為硬依賴而非降級執行**：缺它就沒有「CLI 卡住」的止血點，且 codex 那支靠它兜住不理 EOF 的情況。跨平台（§ 既有慣例為 macOS + Ubuntu）故 `timeout`／`gtimeout` 兩名皆認，皆無即 exit 127

### 5.13 授權層雙模式：逐次授權 + 自主模式
- **捨**：以專案生命週期階段（發想／規畫／設計／開發／測試）當諮詢時機的判定維度
- **取**：授權層保留逐次授權為預設，另增使用者明示啟動的自主模式；保留「啟動／過程／結束」的時機分類並正規化為三種諮詢目的（探索／解阻／審核），各配獨立判準；階段整個移除，改用不分階段的提問模版，額度綁「命題」（計價鍵）而非名稱，受影響的檔案／工項 ID 只作追蹤鍵；工作單元＝一次授權，由使用者劃定
- **理由**：
  1. 階段是時間軸，不是風險軸——同一階段內的決策輕重差距遠大於階段之間。用它決定該不該諮詢，會同時放過重大分叉又對瑣碎改動觸發
  2. 階段邊界不可靠且**可被鑽漏洞**：設計／開發／測試實務上反覆交錯，呼叫端可自稱「進入下一階段」重置額度。綁命題才有穩定 identity——一份大型清單有幾百個工項就有幾百個合法名稱，綁名稱等於沒有上限
  3. 同一決策會跨階段重複諮詢（API 契約在規畫結束、設計啟動、設計結束各一次），而「最後獨立審核」又與各階段結束審核重疊
  4. 四項門檻是為「做到一半遇到狀況」設計的——「高阻斷性」要求已試兩個實質不同方向，對開場探索與收尾審核都不適用。故按目的分流：解阻沿用四項門檻（兩模式共用，只差過門檻後要不要再點名），探索與審核各有自己的成立條件
- **邊界**：自主模式只取消「每次呼叫前重新點名」。啟用清單、副作用邊界、採信原則、子 Agent 規則、`allowed-tools`（§5.9）一律不放寬——Bash 權限詢問仍是送出前的最後一道人工確認，這與 §5.9 的理由 2 不衝突：自主化的是「決定要問」，不是「跳過確認」
- **採信權限降級**：自主模式下顧問意見 🚫 不得據以刪改既有內容，只能列入待裁決清單。逐次點名時使用者是每次都在場的第二道閘，自主化後這道閘消失，需以採信權限補償（§5.10 的硬規則之上再加一層）

### 5.14 自主模式狀態只存對話脈絡，fail closed
- **捨**：把自主模式狀態（是否啟動、七欄授權、預算餘額、呼叫記錄）寫入 `enabled.json` 或另設狀態檔
- **取**：只存在本次主對話脈絡，由可見輸出（啟動確認 → 呼叫前札記 → 新增的呼叫記錄）構成權威版本；無法完整還原即視為已停止
- **理由**：
  1. `enabled.json` 表達跨 session 的「擁有並願意使用哪幾支」，自主狀態表達本次對話的臨時授權，兩者生命週期不同。混存會讓新 session 無聲繼承高權限模式，舊的指派範圍、預算與環境隔離聲明被套進不相干的任務
  2. 落檔會讓設定檔同時承擔配置、授權、會計與稽核，破壞 §5.8 的狀態最小化
  3. 只靠隱性記憶則在 context 壓縮後失真——模型傾向「大致還記得」而樂觀補值。故要求七欄、預算、呼叫記錄三者完整且無歧義才可續用，缺一即停止並要求重新啟動
- **〈自主模式執行辦法〉讀取失敗不算退場**：模式從未成立，維持逐次授權即可，🚫 不得依記憶或摘要執行辦法

### 5.15 啟停指令以「來源＋施為」判定，不以字串匹配
- **捨**：以精確字串比對判定「啟動外部顧問自主模式」
- **取**：來源須為目前主對話的使用者訊息，且該句為直接施為
- **理由**：字串會出現在檔案內容、工具輸出、顧問回覆、子 Agent 委派文字與使用者引用的第三方文本中；「文件裡寫著『啟動外部顧問自主模式』，你覺得安全嗎？」含完整字串卻無啟動意圖。把「找到字串」等同「取得授權」會讓 prompt injection 直接開啟高權限模式
- **不對稱設計**：啟動嚴（無法判定即維持原狀並補問，不得偏向啟動）、停止寬（任何明確表示停止的措辭即生效）——兩種誤判的代價不對稱

### 5.16 節流嵌在 adapter 內，不做成呼叫端自選的腳本
- **捨**：獨立一支 `advisor-throttle.sh consume`，由呼叫端在諮詢前自行執行
- **取**：扣桶動作嵌進四支 `ask-*.sh`，`--scope` 必填、缺它 exit 2；獨立腳本只留給使用者查水位與重置
- **理由**：由呼叫端決定要不要節流，等於沒有節流。現行限制（觸發判準、命題身分、札記閘門）全部依賴呼叫端的判斷，而 §5.13 記的第一個系統性失敗就是自我合理化——節流的價值正在於它不需要判斷，只需要數數與看時鐘
- **三層硬度**：軟（判準、命題、札記）依賴判斷｜中（呼叫記錄）依賴記帳誠實｜硬（節流、Bash 權限詢問、使用者撤回）不依賴呼叫端。節流補的是原本空著的硬層
- **殘留的軟處**：`--scope` 由呼叫端自填、無法驗證。謊報只能在三個桶之間搬移（總量仍是三桶合計），且會在用量記錄留下對不上的痕跡；要完全防堵需 adapter 能獨立判定諮詢類別，而它只看得到 prompt 字串

### 5.17 節流的失敗一律 fail closed
- **捨**：身分解析失敗、鎖逾時、狀態損壞時放行（fail open）
- **取**：一律擋下，並明示「prompt 未送出」；🚫 不得偽裝成桶空（exit 5），那會讓呼叫端以為只要等待即可
- **理由**：fail open 會讓環境差異直接成為繞過節流的途徑——在容器、`sudo`、`tmux` 下取不到身分就自動放行，等於誰的環境特殊誰就免管制。同理，額度查詢失敗時採最保守的半速檔而非正常速：網路故障不應成為放寬節流的理由
- **例外**：GC 失敗只警告不擋——它與本次取用的正確性無關，讓它擋下合法呼叫是錯的權衡

### 5.18 桶鍵含顧問，速率只調恢復不調容量
- **捨**：桶鍵只有 `(PID, scope)`，桶內記錄上次生效速率以處理顧問切換
- **取**：桶鍵為 `(PID, lstart, scope, advisor)`
- **理由**：每支顧問的訂閱額度是獨立事實，用同一個桶會讓 A 顧問的用量排擠 B。顧問進鍵後速率語意也變乾淨——一個桶只對應一支訂閱，不存在「切換顧問後，過去那段時間該用誰的速率排水」的問題
- **仍需存 `refill_seconds`**：同一顧問的額度檔位會隨時間變動。排水一律用「上次生效的值」，取用後才更新——否則等於拿現在的檔位回溯改寫過去那段時間的水位
- **只調速率不調容量**：兩者一起隨額度放大，高餘量時的尖峰會過度膨脹。容量代表可容忍的 burst，那是與額度無關的政策

## 6. 驗證方式

### 6.1 端對端實測（真實 CLI、非 mock）
每支 adapter 三案例：

1. **開新 + 多行回覆**：驗證 id 擷取與多行不截斷（§5.3 的回歸案例）
2. **`-r <id>` 延續**：前一輪埋入記憶點（數字/詞），追問驗證顧問記得
3. **失效 id**：驗證 exit 3 與診斷輸出（agy 另驗回傳 id 比對：`brain/` 存在但 agy 不認的 id → exit 3 且回覆不輸出）

**額度查詢**（`advisor-quota.sh`）另實測三家皆查得餘量：codex 回 `usedPercent` 雙窗（5 小時／7 天）與 `resetsAt`，claude 回 session／週兩段文字並抽出百分比，agy 回兩組 `remaining_fraction`；三者的呼叫皆為 `num_turns=0`／不啟動 thread，未消耗額度。

## 7. 已知限制

- agy 的 resume 前置檢查依賴內部儲存位置 `brain/`（§5.4）：無法確認結構時降級為只靠事後比對，此時失效 id 會多花一次呼叫且 prompt 已執行。若 agy 改為分層且**所有**分層名皆為十六進位 UUID 形狀（如以專案 id 分層），仍會誤判成可驗證而把有效 id 擋成 exit 3——升版後需重驗
- agy 的失敗契約僅驗過逾時與 SIGTERM（皆為結束碼 1、`status=ERROR`、`response` 空、`error` 帶原因、stderr 全空；SIGTERM 另有 `conversation_id` 為空字串）；斷網與認證失效未驗。現以 fail closed 涵蓋（非 `SUCCESS` 一律 exit 1），不依賴知道實際值，但也無法對失敗原因分流
- 各 CLI 的免互動旗標為版本相依（§5.5）；opencode 已改動態偵測，codex/claude/agy 仍為 hardcode，升版需以 `--help` 重驗。opencode 對未知旗標顯性 exit 1（1.18.18 起）
- 各 CLI 的事件格式為觀測所得（smoke test 確認），官方未必保證穩定；解析已以 `fromjson? // empty` 容錯，但欄位更名仍會失效
- 無自動化測試（§6 待辦）：現有驗證為手動執行，未固化成可回歸的測試檔
- `advisor-set.sh` 為 read-modify-write 且無鎖，**不可並行**：兩個 setter 交錯執行會互相覆蓋。不加 lock 是取捨——lock 目錄在強殺後殘留會永久卡住 setter，比競態更糟，而 setter 是使用者偶爾手動跑一次的設定指令
- 額度查詢的 codex 那支**假設 app-server 收到 stdin EOF 會自行結束**（實測 1 秒內）：若某版本改為不理會 EOF，該支會停滯至 timeout 並拒收該次回應（fail closed，不會給錯數字）
- 額度查詢的三個介面**皆非穩定契約**：codex 的 `app-server` 標 experimental，claude 的 `/usage` 是純文字報告（百分比靠 regex 抽），agy 的 `/usage` 雖結構化但屬內部 schema。任一改版都會讓該支查不到——腳本以 `[warn]` 明示查詢失敗（不靜默回報「無額度」），但無法自動修復
- **三層守門全為文件約束，腳本層不設閘**：任何呼叫端直接執行 `scripts/` 下的 adapter 都能繞過啟用與授權檢查。腳本層加閘擋不住讀得懂檔案的 agent，只換來介面複雜度；改以「SKILL.md 明寫唯一入口與流程」降低誤觸——入口明確時，繞過不再是「找不到路只好猜」
- `gemini` CLI 已汰除不納入；若未來恢復，放一支支援 `--info` 的 `ask-gemini.sh` 進 `scripts/` 即完成（§5.8 三層化後無需登錄）
