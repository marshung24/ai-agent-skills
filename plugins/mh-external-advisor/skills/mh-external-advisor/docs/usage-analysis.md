# 用量分析與統計

這份 log 算得出什麼、哪些數字看起來算得出來但會誤導、怎麼用 `advisor-usage.sh`。欄位語意與事件模型的出處在 [usage-log.md](usage-log.md)，本檔不重複。

> 讀本檔的時機：要調節流參數、要確認節流有沒有擋到該擋的、要替這份資料做報表或圖表、或要判斷某個比率能不能算。

## 1. 分析的兩個目的

只有兩個，其餘都不是這份資料的用途：

1. **調節流參數**——容量與恢復速率設得合不合適。
2. **確認節流真的有擋到**——它是不是只是擺著好看。

**🚫 不做「推論使用者習慣再回頭調整呼叫決策」。** 這不是保守，是定義上算不出來：log 只有「曾嘗試呼叫」的事件，沒有「符合資格但最後沒呼叫」的母體，因此觸發率、漏觸發率、precision 這類指標連分母都不存在，樣本再大也一樣。

## 2. 先把分母講清楚

大部分誤讀都來自把不同的分母混稱成「usage」或「request」。至少要分開三個：

| 分母 | 事件 | 意義 |
|---|---|---|
| `throttle_decision` | allow ＋ deny | 節流器做過幾次決策 |
| `call_attempted` | — | adapter 走到啟動 CLI 幾次 |
| `call_finished` (rc=0) | — | 往返確實完成幾次 |

三者逐層遞減，**不可互相代換**。只要命名時混為一談，即使欄位補得再齊，數字仍會說謊。

## 3. 算得出來的

### 直接觀測（可當營運事實）

- allow／deny／reset 事件數，以及按 advisor、宣告 scope、`source`、日期、refill 檔位的切分
- deny 是否曾發生，以及每次 deny 的時間、桶、`remaining_before`、`retry_after_seconds`
- 每筆決策當下的 `capacity`／`cost`／扣款前後水位
- 結束碼分布、往返完成數、結果未知數
- 耗時的 min／中位／max（僅限有 `call_finished` 的樣本）

命名時一律稱「觀測事件」，🚫 不要叫「實際呼叫量」或「工作負載」。

### 帶限定詞可用於調參

- **已記錄決策中的 deny 比例**——名稱必須完整，不可簡稱「拒絕率」
- **接近桶底的 allow 次數**（放行後 `remaining_after < cost`）——是事件計數，不是時間占比
- **同桶短時間內的連續嘗試**——可看出 burst 容量是否真的限制過一串呼叫
- **refill 檔位切換的覆蓋數**——可確認自適應速率確實產生過不同檔位
- **格式與不變量異常**——`remaining` 超出範圍、未知 `event`、無法解析的 principal。這類診斷通常比平均值有用

### principal 分桶完整性（最該先看的一項）

桶是按 principal 分的。若某個名字**每次都是新 PID**，等於它每次都拿到一個滿桶——節流在結構上被繞過，而且是無聲的。

這比整體 deny 比例更貼近「節流有沒有擋到該擋的」。工具會對「事件數 > 1 且 PID 全不重複」的 principal 示警。

## 4. 算不出來的

這些看起來都算得出來，實際會誤導。每項附上推翻它的具體情境：

| 指標 | 推翻它的情境 |
|---|---|
| 平均／中位水位 | 水位只在有事件時取樣。桶在兩次事件之間早就回滿數小時，log 完全沒有那段，事件平均仍會顯得偏低 |
| 低水位時間占比 | 同上，沒有連續取樣。allow 後 remaining=0，十分鐘後回滿且整天沒再呼叫，不能說整天都在低水位 |
| allow 數 ＝ 實際呼叫數 | 扣桶後 adapter 可能在啟動 CLI 前就中止；也可能是有人手動跑 `consume` |
| deny 數 ＝ 所有被擋的呼叫 | 身分／鎖／狀態失敗走另一種 fail closed，**不寫事件**（見 usage-log.md §4） |
| deny 比例 ＝ 節流政策好壞 | 重試策略同時改變分子與分母。被 deny 後立刻重試十次會讓比例暴增；遵守 `retry_after` 則只有一筆 |
| 全域每分鐘 allow 數 ＝ 吞吐 | 桶是按 `principal × advisor × scope` 分的，不是全域桶。十個程序各取三次都可 allow，每個桶都完全合規 |
| 按 `comm` 合併成一個桶 | 真正的桶鍵含 `id` 與 `lstart`。兩個同名程序各有獨立容量，合併會錯判系統放行超過上限 |
| 用 `label(PID)` 長期識別桶 | PID 會重用。文字鍵相同，實作上卻因 `lstart` 不同而是兩個桶 |
| 從 `remaining` 差值反推 cost | 事件之間會補水，速率也可能切檔。`20 → 14` 不代表成本是 6 |
| 用本筆 `refill` 解釋上一段恢復 | 實作先用舊速率排完過去時間，最後才切新值。用本筆的值回算會憑空多出恢復量 |
| 比較各 refill 檔位的成效 | 檔位由顧問剩餘額度決定，**不是隨機分派**。慢檔天然出現在餘額偏低時，差異來自時期而非參數 |
| 「容量應該調到 N」 | log 沒有「可接受的等待」與政策目標。同一串四連發，既可讀成容量該調大,也可讀成第四次正該擋 |
| 對新參數做反事實 replay | 缺歷史設定與桶重建紀錄。桶因 incarnation 改變而重建成滿桶，replay 會接到舊桶，結果完全不同 |
| 長期趨勢／月成長率 | 按 byte 輪替、只留兩代。高流量期很快覆蓋舊資料，低流量期保留較久，時間窗口長度不固定 |

## 5. 工具

```bash
scripts/advisor-usage.sh                     # 全部
scripts/advisor-usage.sh --advisor codex     # 只看某支顧問
scripts/advisor-usage.sh --scope review      # 只看某個宣告 scope
scripts/advisor-usage.sh --since 2026-09-01  # 只看某日之後
scripts/advisor-usage.sh --json              # 機器可讀，同一組數字
```

唯讀，不改任何狀態。結束碼：`0` 成功、`1` 解析失敗、`2` 參數錯誤、`4` 查無資料、`127` 缺 `jq`。

輸出四區，每區都先講資料邊界再給數字：

1. **資料品質與窗口**——時間範圍、事件數、舊格式行數、best effort 警告
2. **節流證據**——決策數、deny 比例與明細、發起來源、reset 次數
3. **呼叫結果**——嘗試送出／已完成／往返完成／結果未知、結束碼分布、耗時
4. **調參觀測**——advisor×scope 交叉、refill 檔位分布、接近桶底次數
5. **principal 分桶完整性**——見 §3

`--scope` 的過濾會經 `invocation_id` 回推到生命週期事件：`call_attempted` 與 `call_finished` 本身不帶 `declared_scope`，直接比對會把它們整批濾掉，報出「已送出 0」這種假數字。

## 6. 報表與圖表

**第一版刻意不做圖。** 表格與明細比 dashboard 更能避免把不完整的事件資料誤讀成工作負載或成功率，而圖表會讓資料看起來比實際成熟。

要畫之前先確認樣本撐得住。以單一顧問、百來筆事件、其中 deny 個位數的資料為例，這些**不該畫**：圓餅圖（樣本小又單一維度，視覺上放大成熟度）、桶使用率折線（事件取樣畫成折線等於虛構事件之間的狀態）、成功率與 P95 延遲（除非 `call_finished` 已累積足量）、每 incarnation 呼叫數直方圖（PID 不是人）、scope 間需求比較（宣告維度，且各 scope 參數可能不同）。

生命週期事件累積起來之後，兩張就夠：

- 每日 `call_attempted` 與 `deny` 數
- deny 的時段分布與 `retry_after_seconds` 分布

畫任何一張圖都要標**資料窗口**與**該圖用的是哪個分母**。

## 7. 這份資料能下的最強結論

以目前的欄位，能講到的極限是：

> 此快照證明節流器至少拒絕過一次已耗盡桶的取用，且該分支依契約不會送出 prompt。此資料源**不能**證明所有應受節流的呼叫都經過節流器。

要再往前一步——例如證明沒有繞過路徑——需要的不是更多樣本，是這份 log 之外的獨立證據。
