## 一、完整改寫案例

> **範例事實原則**：改寫後案例中的具體事實（功能、日期、數字）示意「作者已提供資料時」的目標狀態。實際改寫遇缺料時，依案例 7 的做法標記〔需作者補充：……〕或詢問，不得編造。

### 案例 1：技術文件（大陸用語 + 翻譯腔）

**改寫前：**
> 该系统通过负载均衡和消息队列实现高可用架构。当服务器宕机时，系统会无缝切换至备用实例，确保用户的访问不受影响，为业务连续性保驾护航。

**改寫後：**
> 系統以負載平衡和訊息佇列達成高可用性。伺服器當機時會切換到備用執行個體，使用者的存取不會中斷。

**所做更改：**
- 簡轉繁＋詞彙轉換：负载均衡→負載平衡、消息队列→訊息佇列、宕机→當機、实例→執行個體、用户→使用者、访问→存取
- 刪除「无缝」（翻譯腔）、「确保……不受影响」（句尾附加）
- 刪除「保驾护航」（陸式商務腔）

### 案例 2：規範文件（約束強度不得漂移）

**改寫前：**
> 所有对外接口都应该尽量使用 HTTPS。开发者最好不要在日志中输出用户的敏感信息，建议在代码评审时重点关注。

**改寫後：**
> 對外介面**必須**使用 HTTPS。日誌**不得**輸出使用者的敏感資訊；code review 時列為必查項。

**所做更改：**
- 詞彙轉換：接口→介面、日志→日誌、代码评审→code review（台灣慣用直寫英文）
- **約束強度依原規範意圖對齊**：本例作者確認這兩條是硬規定，「应该尽量」「最好不要」是 AI 生成時的軟化漂移，改回「必須」「不得」。反過來，若原文的「建議」就是建議，不得擅自升級成「必須」——升降級都要作者確認，不確定時標記詢問

### 案例 3：設計文件（保留 trade-off 與決策理由）

**改寫前：**
> 在快取策略上，各方案各有優缺點，需要综合考虑多方面因素。经过深入分析，我们最终选择了 Redis，它能为系统性能保驾护航，赋能业务的高速发展。

**改寫後（作者已提供：取捨理由）：**
> 快取選 Redis 而非本機記憶體快取：我們有三台 API 節點，快取需要跨節點一致；代價是多一個依賴服務，由 SRE 例行監控吸收。

**所做更改：**
- 刪除「各有優缺點、綜合考慮多方面因素」（立場真空，X1）——設計文件必須寫出選了什麼、捨了什麼、為什麼
- 刪除「保驾护航」「赋能」（陸式商務腔）
- **trade-off、假設與決策理由是設計文件的核心資訊**，改寫只能讓它更清楚，不能刪短；缺料時標〔需作者補充：選擇理由與代價〕，不代作者選邊

### 案例 4：教案（保留教學功能）

**改寫前：**
> 本节将介绍闭包的概念。闭包是一个非常重要且强大的特性，掌握它将为你的编程之旅打开新的大门。首先让我们回顾上一节的作用域知识……

**改寫後：**
> 本節介紹閉包（closure）。先回顧上一節的作用域：……

**所做更改：**
- 詞彙轉換：闭包→閉包（首次附英文原詞）、编程→程式設計
- 刪除「非常重要且强大」「打开新的大门」（空泛價值宣稱，模式 1、4）
- **保留**「本節將介紹」「首先讓我們回顧」——預告句與步驟導引在教案有導覽功能（X13 教案豁免），只精煉不刪除；學習目標、前置知識、重複提示同理

### 案例 5：程式註解（identifier 不動，說明好懂）

**改寫前：**
```js
// 通过异步回调获取用户数据，若缓存命中则直接返回，否则发起网络请求，
// 该函数是整个数据层的核心枢纽，发挥着至关重要的作用
async function getUserData(uid) { ... }
```

**改寫後：**
```js
// 取得使用者資料：快取命中直接回傳，未命中才發網路請求
// I/O：uid (string) → Promise<UserData>；快取失效邏輯見 invalidateCache()
async function getUserData(uid) { ... }
```

**所做更改：**
- 詞彙轉換：异步→非同步（本例句子重寫後不需出現）、缓存→快取、网络→網路
- 刪除「核心樞紐、至關重要的作用」（空泛價值宣稱）——註解寫用途與 I/O，不寫重要性
- **函式名、參數名、被引用的 identifier 一字不改**；補上 I/O 說明是讓註解符合團隊註解原則，前提是資訊來自程式碼本身，不是編造

### 案例 6：過度口語化的反例（「略微口語」的邊界）

**原文（正式公告）：**
> 本行預計於 3 月 15 日凌晨 2 時至 5 時進行系統維護，期間網路銀行服務將暫停。

**錯誤改寫（過度口語、破壞文體）：**
> 跟大家說一下～我們 3/15 半夜要修系統啦，網銀會掛掉幾個小時，大家忍耐一下囉！

**問題：** 「改得好懂一點、略微口語」的底線是**語域不降級**。正式公告、規範、法務文字需要精確與禮貌程度；「有人味」不等於強塞口語、表情或裝熟。此文沒有 AI 痕跡、也沒有難懂之處，正確處理是不改。「進行系統維護」的「進行」在公文語體屬可接受用法，可改可不改。

### 案例 7：不得虛構事實的正反例

**原文：**
> 專家認為此政策將帶來深遠影響。

**錯誤改寫（捏造來源）：**
> 台大經濟系教授在 2025 年的訪談中指出，此政策將使中小企業成本增加一成。

**正確改寫：**
> 〔需作者補充：具體來源；無法補上則刪除此句〕

改寫**不能新增事實**：不虛構引言、作者經驗、數字，不把模糊歸因改成假的明確來源，不為了增加人味捏造猶豫、失敗或個人故事。

## 二、文體保真

### 有寫作樣本時
- 分析樣本的句長分布、稱謂習慣（你／您）、口語程度、標點習慣、常用詞
- 改寫以樣本為準，而非套用「理想文風」
- 樣本本身有 AI 痕跡時，只移除痕跡，不改變作者的其他習慣

### 沒有樣本時
- 依原文文體保守改寫：只處理明確的 AI 模式與難懂處，不做風格再造
- 規範維持規範的約束語氣；技術文件維持術語一致；教案維持導引結構
- 不確定作者意圖的表達（可能是刻意的），標記詢問而非直接改掉

### 文類原則

各文類的保留項與禁改項見 SKILL.md「文類規則」。跨文類的原則只有一條：**在不違反文類必要格式、精確性與專案規範的前提下，保留作者聲音**。作者在技術文件裡固定用第一人稱、固定用某個詞序，那是習慣，不是待修的偏差；但規範格式、法務措辭、學術引用體例與專案詞彙表優先於個人習慣。文類規則管的是必要精確度與語域，不是把所有人的文字磨成同一種。
