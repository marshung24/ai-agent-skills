# 保護對象與誤殺防護

改寫應優先避免改壞事實。動筆前先圈出不能動的內容，改寫全程原封不動；改完回頭逐項核對。

## 兩層保護級別

| 層級 | 意義 | 處理方式 |
|---|---|---|
| **原樣保留** | 動了就是改壞：技術字串、數字與版本、專名、引用原文 | 逐字保留，改寫全程繞過；發現明顯錯誤時標註提醒作者，不代改 |
| **只標記，不自動改** | 可能該改，但判斷權在作者或專案規範 | 列出位置與理由，等作者決定 |

其餘可改寫的內容仍受「[可調表達，不可調語意](#可調表達不可調語意)」與「[語意保真規則](#語意保真規則)」約束。

## 第一層：原樣保留

### 技術字串

- 程式碼區塊與 inline code、CLI 指令、錯誤訊息、需精確重現的 UI 字串
- identifier：class／function／property／變數名、API 名稱、HTTP method 與 status code、header 名、環境變數
- 資料結構：JSON/YAML 鍵值、DB table 與 column 名、metric 名、log 欄位
- 文件機制：URL 與檔案路徑（含全部查詢參數——本 skill 不清理追蹤參數）、Markdown anchor、front matter、交叉引用標籤
- 這些內容中的大陸用語、半形標點、AI 味句型一併保留——精確重現優先於在地化

### 數字、版本與條件

- 日期、時間、數量、統計數據、成效指標、版本號、期限
- **精度不得漂移**：「約 42%」不能變成「超過四成」，「三到五天」不能變成「大約一週」；反方向同樣不行——原文模糊的不得被改寫成看起來精確的數字
- **絕不為了「更具體」補上原文沒有的數字**。具體化靠作者提供事實，不靠改寫者估算

### 專有名詞與引用

- 產品名、專案名、課程名、機構全銜、品牌與產品正式名稱——不因模式 11（同義詞循環）被替換成泛稱（作者慣用的簡稱除外）
- 中國平台與產品的正式名稱照原文（小紅書、公眾號），不套用 lexicon 的用語替換表
- 逐字引用的法規條文、原文引用、引用文獻標題；引號內的原話一字不改
- 真實姓名不得被替換成「這位受訪者」之類的泛稱；匿名化是作者的決定，需要時標記詢問，不主動代為模糊化

## 語意保真規則

可改寫的敘述文字，表達可以修，**語意等值必須逐項守住**——技術文件與規範最常見的改壞不是詞不好，而是改寫時語意悄悄位移：

- **規範語意詞不得互換**：必須／應／得／不得／禁止／建議／可選／預設／棄用（及 MUST／SHOULD／MAY 等 RFC 關鍵詞）各有明確的約束強度，改寫不得升降級
- **版本與範圍關係不得走樣**：`>= 3.2` 改寫成中文時不得遺漏等號語意——寫「3.2（含）以上」，不寫有歧義的「3.2 以上」
- **邏輯量詞不得替換**：全部、任一、至少、至多、僅限——各自劃出不同的集合
- **條件、例外、否定與因果方向不得翻轉或脫落**：「除非 A 否則 B」「僅在 A 時 B」的結構逐項核對
- **可能性不得變確定性**：「可能造成」不能變「會造成」；反向也不行——作者的確定判斷不得被改寫加上「或許」
- **責任主體不得改模糊**：誰負責、誰核准、誰承擔，主詞不得在改寫中消失

## 第二層：只標記，不自動改

專有名詞的譯法、兩岸法規名稱、中國產品的正式 UI 用字、作者刻意使用的地域語言、學術領域固定譯名、「台灣／臺灣」等組織用字規範（重點是全篇一致，依專案詞彙表為準）、可疑引用（模式 X14）、原文遺留的模板佔位符（模式 X12）、連結上的可疑追蹤參數。

## 可調表達，不可調語意

- **正式語域**：公告、規範、法務措辭可以刪冗贅、拆過長句，但不得改成聊天口吻——「略微口語化」的底線是語域不降級
- **教學語言**：教案的重複提示、步驟導引、預告句有教學功能，可精煉但不刪除功能本身
- **註解**：可台灣化、可改好懂，但前置／後置條件、輸入輸出格式、DECISION 取捨理由的資訊點一項不少

## 容易誤殺的情況

規則對了、判斷錯了，一樣改壞。這些情況先放行：

| 看起來像 | 其實是 | 判斷方法 |
|---|---|---|
| 三段式列舉（模式 10） | 承載真實對比的修辭或規格並列 | 每一項底下有沒有具體事實？有就放行 |
| 編號與表格 | 步驟、SOP、參數表、規格對照 | 文件結構預設保留（見 patterns.md 開頭硬規則） |
| 模糊歸因（模式 5） | 有出處的資料 | 「根據我們後台的數據」出處明確，放行 |
| 否定式排比（模式 9） | 承載核心轉折的用法 | 兩邊都有實質內容、沒有形成密集重複就放行，沒有出現次數上限 |
| 過度限定（模式 23） | 規範的限制條件、學術的邊界聲明 | 「在 X 條件下」承載真實限制就是精確度，不是迴避 |
| 重複句式（模式 11） | 教案的重複提示、長文的節奏設計 | 重複有沒有在推進理解？有就是設計 |
| AI 高頻詞（模式 7） | 被討論的對象 | 「我戒掉了『賦能』這個詞」是提及不是使用 |
| 空泛的「優化」 | 掛著具體動作與指標 | 後面接得出「改了什麼、變化多少」就放行 |
| 陸式用語（lexicon 第 4 類） | 同形異義的正常用法 | 物理量的「質量」、法律的「程序」、公文的「文件」——見 lexicon 不可機械替換清單 |
| 中英夾雜（T4） | 必要術語與正式產品名 | API、SDK、metadata、token 等無慣用中譯者保留 |
| 正式函文禮貌語（模式 21） | 語域要求 | 涉及責任、規範的制式語保留 |
| 口語碎片、不完整句 | 作者原有的聲音 | 這是要保護的方向，一個字都不動 |

拿不準時的通用判準：**這句話刪掉或改掉之後，讀者少知道了什麼？** 少知道任何事實、條件或立場，就不能刪；什麼都沒少，才是空話。

## 回讀核對程序

改寫完成後依序執行，任何一項失敗就回去修正，不交付：

1. 把動筆前圈出的保護對象列成清單（技術字串 N 項、數字與版本 N 項、專名 N 項、連結 N 項、引用 N 項）
2. 在改寫版逐項搜尋，確認存在且逐字一致
3. 確認數字精度沒有漂移（第一層「數字、版本與條件」）
4. 確認規範語意詞、邏輯量詞、條件與因果方向逐項等值（語意保真規則）
5. 確認原文每個資訊點（事實、數字、判斷、行動、取捨理由）在改寫版都找得到
6. 確認沒有新增原文沒有的事實、數字或來源
7. 確認作者立場沒有翻轉或稀釋（「我反對」不能變成「我持保留態度」）
8. 確認語域一致：規範仍像規範，教案仍像教案，註解仍像註解
9. 確認刪掉的套話沒有被同族的另一句套話取代（刪「標誌著」不能補「象徵著」；刪「賦能」不能補「加值」）
