# issue 紀錄設計草稿

> 要討論或評估 `backlog/issues/` 時讀本檔；讀了得到分類方式、與 request 的關聯、揭露邊界的繼承原則與未決事項。
> **草稿、未啟用**：不授權任何讀寫或揭露，AI 執行時不以本檔為依據；現行規則以 [collaboration.md](../references/collaboration.md)〈揭露邊界〉〈登錄檔〉為準。

## 目的

之後以 issue 追蹤跨多則請求的工作，並能在 Telegram 上與本來就知情的對象溝通，不讓任何人因查詢紀錄得到原本不知道的內容。此原則只管紀錄查詢，不管首次任務成果回報與私訊核准。

## 分類與關聯

- **分類**：依專案分，`data/backlog/issues/<專案>/`；專案名只用 `internal.md`〈專案〉已有者
- **關聯**：一個 issue 可涉及多筆 request，逐筆記來源（聊天室 ID／訊息 ID）；issue 不複製 request 內容
- **專案歸屬不等於可揭露**：放在某專案下，不因該專案對外公開＝Y 就能談

## 揭露邊界的繼承

issue 沒有自己的揭露範圍，一律由涉及的 request 推得；判定只看來源聊天室，不看 request 的受眾欄：

| 問的是 | 判定 |
|---|---|
| 整體（摘要、總狀態、關聯、數量、合併關係） | 所有 request 都來自發問的聊天室才可答；有一筆不同即不提供 |
| 局部（某一筆 request 的部分） | 只答當前來源那一筆依〈揭露邊界〉「請求查詢」可談的內容 |
| 證據不足（關聯不完整、來源不明） | 整體不提供；🚫 不略過未知來源 |

- **不提其他部分**：不說還有幾筆、有其他來源、有部分無權查看，也不帶出整體進度
- **同一人在兩個聊天室**：不因此取得跨聊天室查詢權

例：

- 同來源：同群的 request A、B 併成一個 issue，在該群問整體進度 → 可答
- 跨來源：群組 G1 的 A 與私訊的 B 併成一個 issue，在 G1 問 → 只答 A 的部分，不提 B
