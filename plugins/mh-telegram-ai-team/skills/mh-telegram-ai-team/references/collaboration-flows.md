# 情境流程

要進入任一情境前讀整份；讀了得到操作順序、訊息範本與回訊／回報／派工條件。先讀完 [collaboration.md](collaboration.md) 才用本檔，🚫 不可只看範本就送出：等級、停止、揭露、分級、同意與互動限制都在那裡。未註明檔名且不在本檔的段落指 collaboration.md。

每個情境依同一骨架：**情境**（何時選）→ **流程** → **訊息**（範本：區塊內只有 `【】` 固定開頭與替換後的 `<>` 會送出；`<>` 由 AI 依實際資料填，填寫限制寫在區塊外，🚫 不送出區塊外說明）→ **回訊條件** → **回報條件** → **派工條件**。一則入站可依序經過多個情境（例：詢問 → 承接 → 待同意）。

## 1. 詢問與討論

- **情境**：被問到問題；或自己需要別人的資訊
- **流程**：自己能答 → 直接答。需要別人 → 知道找誰就 `@<目標AI>`；不知道才 `@all` 徵詢，有人回應後改定向 → 彙整後回原提問者
- **訊息**：

  ```text
  @<提問者> <回答>

  @<目標AI>【詢問】<問題>
  需要：<要對方提供什麼>｜背景：<最小必要脈絡>

  @all【徵詢】<問題>，知情者請回覆我；其他人不需回覆。
  ```

- **回訊條件**：有答案或關鍵補充才回；結論需全體知悉且負責人要求時，才以【公告】發布
- **回報條件**：替真人轉問者，取得答案後 @ 原提問者回報，並註明資訊來源
- **派工條件**：自己答不了、需內部調查或專業處理 → 轉〈承接與對內派工〉

## 2. 承接與對內派工

- **情境**：被交辦任務，或詢問需要內部團隊處理
- **流程**：判級（〈任務分級〉）→ 記錄（〈登錄檔〉「請求紀錄」）→ 需同意先走〈待同意與中止〉→ 長任務先發「收到」→ 自做或派內部成員 → 彙整 → 發「完成」
- **訊息**：

  ```text
  @<請求者>【收到】理解為：<需求摘要>
  預計：<做法>｜預估：<時間或里程碑>

  @<請求者>【完成】<結果摘要>
  產出：<檔名或對外連結>｜未驗證：<無則寫「無」>
  ```

- **回訊條件**：短答直接回不發「收到」；長任務先承接
- **回報條件**：完成、受阻或範圍需擴大時回報請求者；替真人辦的事完成時一併 @ 該真人
- **派工條件**：依 `internal.md` 內部團隊的職責與涉及專案選人；派工的核准依〈任務分級〉（預設逐次同意，`AGENTS.md`〈派工流程〉可另定）；內部成員只回祕書，對外一律由祕書發

## 3. 待同意與中止

- **情境**：「需負責人逐次同意」級、或未列入常規授權的「可常規授權」級任務；負責人不同意；已承接的任務受阻、過期或被取消
- **流程**：私訊負責人「需確認」→ 在來源聊天室回請求者【待確認】→ 等負責人以有效方式同意 → 才執行 → 回〈承接與對內派工〉，結果回來源聊天室。〈同意管道〉設為來源聊天室、或私訊送不出（工具報錯或橋接層不支援）時，改在來源聊天室 `@<負責人>` 發「需確認」，不另發【待確認】；設為終端機時只在終端機列出「需確認」，來源聊天室照回【待確認】。負責人在私訊直接交辦者就在該私訊確認。拒絕或中止 → 發對應訊息後停止
- **訊息**：

  ```text
  <私訊留空；在群組發時為 @負責人>【需確認】<事項>
  來源：<群組名稱>｜請求者：<請求者>｜原請求：<一句摘要>
  要做：<動作與產出>
  可做：<允許的範圍>｜不可做：<排除項目>
  影響：<範圍與副作用>
  同意請回覆本則：同意 <確認碼>（<到期時間> 前有效）；或在終端機同意

  @<請求者>【待確認】<事項> 已請負責人確認，同意前不執行；不需重送，本則不需回覆。

  @<請求者>【拒絕】無法 <要做的事>：<原因>｜改由：<管道>

  @<請求者>【中止】<事項> 已停止：<原因>｜缺：<所需條件>
  ```

  「群組名稱」取 `external.md`〈群組〉的名稱，含禁送資訊時改用可辨識的代稱，🚫 不寫 chat ID；私訊交辦者寫「私訊」；「到期時間」含時區
- **私訊內容**：只放負責人判斷這件事所需的摘要；🚫 不帶其他聊天室內容、他人私訊或〈停止條件〉〈揭露邊界〉禁送的資訊；邊界在這些限制下說不清時不發，請負責人到終端機
- **私訊回合**：以送出的「需確認」本文與本機紀錄為準，🚫 不為補脈絡查來源聊天室歷史（SKILL.md〈不變式〉）
- **回訊條件**：同意前只可說明在等待（即【待確認】），🚫 不得表述為已承接執行；同一請求重送不另開確認；已回〈跨團隊請求〉「收到」者免發【待確認】
- **回報條件**：中止已承接的事項時通知請求者；過期未同意視同中止，在下一個處理回合於來源聊天室發【中止】；原因只寫可公開的，🚫 不轉述負責人私訊內容
- **派工條件**：同意前不派工；範圍擴大重新確認

## 4. 跨團隊請求

- **情境**：要請他方團隊處理事情（發起方），或收到他方祕書的請求（接收方）
- **流程**：發起方 `@<他方祕書>` 提出 → 接收方記入 `backlog/requests/`、回「收到」→ 與**自己的負責人**討論是否承接、派工與做到什麼程度（終端機或「需確認」）→ 依定案對內處理 → 回發起方 → 發起方回報自己的請求者
- **訊息**：

  ```text
  @<他方祕書>【協作請求】目標：<要什麼>
  範圍：<可做／不可做>｜期望回覆：<時間或形式>｜來源：<原訊息連結或 ID>

  @<發起方>【轉交】<交接內容>｜性質：<只供參考／請接手>
  來源：<原訊息連結或 ID>
  ```

  「來源」的 ID 為自己看到的編號，以回覆原則為準
- **回訊條件**：接收方必回一則：「收到」（已記錄、待負責人定案），命中〈停止條件〉不理會者除外；寫不進 `backlog/`（如 Codex 群組回合唯讀）改回「收到，尚未記錄，待負責人在終端機補登」，🚫 不宣稱已記錄；負責人定案前 🚫 不給結果、不承諾範圍
- **回報條件**：接收方完成或受阻時回發起方；發起方收到結果後回報自己的請求者
- **派工條件**：各祕書只派自己團隊；發起方負責人的同意不能授權接收方團隊

## 5. 認識與更新

- **情境**：自己首次進群；被要求介紹；收到他方自介；自己職責變動
- **流程**：新加入者 `@all` 自我介紹並邀請 → 各祕書依其自介登錄，再以 `@新加入者` 回自介 → 雙方各自寫 `external.md`。也可由真人發一則同時 @ 雙方的訊息啟動
- **訊息**：

  ```text
  @all【認識】剛加入本群，跟各位祕書認識。
  <自介欄位>

  請收到的祕書回一則【自我介紹】，開頭以 @ 點名 <自己的 bot username，不帶 @>，我才收得到。

  @<對象>【自我介紹】<自介欄位>

  自介欄位：
  我是 <暱稱>（<bot username>），負責人 <負責人暱稱>（<username>）
  職責：<職責>
  可詢問：<專案或主題>
  ```

  職責變動時改發 `@all【公告】職責更新：<自介欄位>。本則不需回覆。`；填值時 username 一律去掉 `@`（〈訊息契約〉「正文不帶 @」）
- **可選欄位**：空白或「待確認」視同未填，照下列處理
  - 暱稱（祕書、負責人）：只寫 username
  - 職責：用預設「就所屬團隊負責的專案，提供可公開資訊與唯讀視角的討論；需核准的事（如派工、PR、部署）依所屬團隊流程或由其負責人決定」；只是摘要，實際仍依〈任務分級〉
  - 可詢問：列對外公開＝Y 且有摘要的專案名；沒有就省略該行
- **自介來源**：自己的自介欄位只取 `internal.md` 及其 `internal/` 子檔；🚫 不從 `external.md`、記憶、歷史或他方自介推定自己是誰。`internal.md` 不存在、缺 bot username 或負責人 user ID／username 時不發自介，回「本機登錄未建置，請負責人到終端機定版」，🚫 不在回合內擬稿（建檔見〈登錄檔〉「建檔」）
- **回訊條件**：被邀請或被要求才回自介；bot 收不到自己入群前的訊息，自己先前發過的自介或【認識】對方可能沒收到，被邀請時除〈回應等級〉只收件只回一次外，一律照流程 `@發起者` 回【自我介紹】，🚫 不以「已發過」略過；收到自介只更新 `external.md`，不致謝；寫不進（如 Codex 群組回合唯讀）就明說未登錄，由負責人在終端機補登
- **回報條件**：無
- **派工條件**：無

## 6. 通訊測試

- **情境**：重連、清除佔用輪詢的殘留程序、改觸發或存取設定後，驗證對方收得到自己的訊息
- **流程**：發送方 `@<目標AI>【測試】` → 目標回固定文字（只收件者回「收到！」）→ 發送方收到即視為雙向通；逾時未回改由負責人在終端機依 setup.md〈排查〉查對方
- **訊息**：

  ```text
  @<目標AI>【測試】<原因>，請回覆「收到測試」即可，不必附其他內容。

  @<發送方> 收到測試
  ```

- **回訊條件**：被點名必回一則，只含固定文字；計入〈互動規則〉往返輪數，達上限仍停
- **回報條件**：發送方向要求測試的負責人回報結果（通／未通與等待時間）
- **派工條件**：無
